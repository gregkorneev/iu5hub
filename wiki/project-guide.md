# Подробный путеводитель по проекту

Этот документ описывает устройство репозитория и основные пользовательские и технические сценарии. Он помогает найти нужный код и профильные инструкции; для операций с production, секретами и данными сначала читайте соответствующие страницы Wiki. Описание основано на состоянии кода в ветке `beta`; фактическое состояние развертываний и неподтверждённые проверки отмечены в [current-state.md](current-state.md) и [deployment.md](deployment.md).

## Назначение и границы продукта

«Студент ИУ5» — Telegram Mini App для доступа студентов к учебным материалам и расписанию. Пользователь открывает приложение из бота, выбирает курс и перемещается по публичным папкам Яндекс Диска, ищет размеченные предметы и преподавателей, сохраняет файлы и папки и выбирает учебную группу. Поддержка работает в личном чате бота. Служебная статистика доступна только администраторам.

Тяжёлые файлы остаются на Диске. Frontend размещён как статический сайт на Cloudflare Pages, а отдельный Worker с D1 обеспечивает приватные функции и webhook бота. Адрес Pages — технический адрес Mini App; локальный браузер удобен для разработки, но не заменяет проверку внутри Telegram. Telegram-контекст интерфейса сам по себе не является серверной авторизацией.

## Пользовательские сценарии

1. **Каталог.** На главной находятся три курса и полезные ссылки. На экране курса приложение запрашивает содержимое открытой публичной папки, показывает подпапки и файлы и позволяет переходить по дереву или открывать файл. Семестровые папки получают специальное представление. Ошибка загрузки и пустая папка отображаются отдельно. Конфигурация корней — `src/data/courses.ts`; второй и третий курсы используют вложенный `rootPath` внутри общего публичного ресурса.
2. **Поиск.** Поиск и подсказки работают по локальному сгенерированному индексу размеченных папок. Запрос нормализуется и сопоставляется с началом тега или имени преподавателя без учёта регистра; результат открывает папку курса. Это не полнотекстовый поиск содержимого файлов и не обход Диска при вводе. Название и родительский путь помогают различить одноимённые результаты. Процесс разметки и пересборки — [search.md](search.md).
3. **Избранное.** Сердце сохраняет папку или файл в личном профиле; операции синхронизируются с Worker. Список группируется по типу, папку можно открыть, файл — получить через Диск. Если сохранённая папка больше недоступна, интерфейс предлагает удалить её. Подробнее о модели, optimistic update и ошибках — [profile.md](profile.md).
4. **Расписание.** Пользователь выбирает группу в расписании, профиле или при знакомстве с приложением. Статические данные показывают занятия по датам; отсутствие опубликованного расписания — отдельное состояние. Сохранение группы работает локально и, при проверенном Telegram-сеансе, через Worker. В личном чате также предусмотрен виджет по `/schedule` или кнопке «📅 Расписание»; фактическую доступность webhook нужно проверять по текущему состоянию развертывания. См. [schedule.md](schedule.md).
5. **Поддержка и администрация.** Сообщения в личном чате бота передаются разрешённым администраторам, ответы пересылаются обратно ботом. Страница статистики и команда `/stats` защищены серверной проверкой. См. [support.md](support.md), [analytics.md](analytics.md).

Нижняя навигация содержит каталог, поиск, расписание и профиль; статистика администратора размещена отдельно. Telegram BackButton и возврат внутри интерфейса учитывают контекст маршрута. Приложение адаптирует тему и безопасные отступы к Telegram, а также имеет состояния загрузки, ошибок и отсутствующих данных.

## Компоненты и потоки данных

```text
Telegram → Mini App / Cloudflare Pages → React + HashRouter
                                     ├→ публичный API Яндекс Диска → папки и файлы
                                     ├→ статический индекс тегов → поиск
                                     ├→ статический JSON Pages → расписание
                                     └→ Worker /api/* → D1 (профиль и аналитика)
Telegram Bot API → защищённый webhook Worker → поддержка / статистика / виджет
LKS → ручной или запланированный sync → проверенные JSON расписания → Pages
```

Каталог, поиск и расписание имеют разные источники: изменения файлов на Диске видны при следующей загрузке соответствующего каталога, но сами по себе не создают поисковую разметку; расписание обновляется отдельным pipeline и при открытии не запрашивает LKS. Избранное хранит ссылки на объекты, а не копии материалов. Перенос или удаление папки может сделать ранее сохранённый путь недоступным.

### Frontend

| Расположение | Ответственность |
| --- | --- |
| `src/main.tsx`, `src/App.tsx` | Точка входа, `HashRouter`, маршруты, общая компоновка и основные экраны каталога, поиска и профиля. |
| `src/components.tsx`, `src/Welcome.tsx` | Общие элементы интерфейса и первое знакомство с приложением. |
| `src/domain/`, `src/data/` | Типы, предметные преобразования и конфигурация курсов/статических материалов. |
| `src/repositories/` | Доступ к каталогу Диска и поиск по индексу; компоненты не должны реализовывать протокол поставщика. |
| `src/profile/`, `src/schedule/` | Состояние избранного и экран расписания с настройкой группы. |
| `src/telegram/` | Обёртка Telegram WebApp: тема, viewport, навигация, внешние ссылки и другие возможности клиента. |
| `src/api.ts`, `src/analytics.ts`, `src/AdminStats.tsx` | Адрес Worker и заголовки, события и административная статистика. |
| `src/generated/`, `public/data/schedule/` | Генерируемый индекс поиска и опубликованные статические данные расписания. Не редактируйте результаты генерации вместо источников. |
| `src/*.css` | Базовые стили, токены, темы, каталог и адаптивные правила. |

Маршруты используют hash-фрагмент, поэтому серверу статических файлов не нужен fallback для каждого пути. Основные пути: `/`, `/course/:id?path=...`, `/search`, `/schedule`, `/profile`, `/admin/stats`. В коде также сохранены `/semester/:id`, `/subject/:id`, `/subject/:id/:category` и `/material/:id`; неизвестный путь открывает страницу ошибки. Состояние маршрута сохраняет контекст перехода из поиска или избранного. Подробнее о Telegram-инвариантах — [telegram.md](telegram.md).

### Worker и D1

`worker/src/index.mjs` обрабатывает HTTP API и webhook; `telegram.mjs` отвечает за проверку Telegram и идентичность, `support.mjs` — за relay, `schedule-widget.mjs` — за виджет. Схема D1 развивается последовательными миграциями `worker/migrations/0001…0007`: аналитика, избранное, настройки группы, маршрутизация поддержки, метки username, историческая сводка и дедупликация обновлений Telegram. Это разные наборы данных с разными сроками и назначением; подробности — в профильных страницах и самих миграциях.

Для персональных API сервер проверяет подписанный `initData`, а для административных дополнительно сверяет проверенный ID с allowlist. Worker выводит ключевые HMAC-псевдонимы серверными секретами; избранное и настройки используют отдельный ключ от аналитики. `initDataUnsafe`, имя пользователя или скрытие кнопки в интерфейсе не доказывают права доступа. В поддержку входят зашифрованные идентификаторы для маршрутизации ответов. Не помещайте секреты в репозиторий или `VITE_*`: переменные Vite попадают в публичную сборку. Политика хранения и защиты — [security.md](security.md).

## Источники данных и сопровождение

| Данные | Источник истины | Как обновлять |
| --- | --- | --- |
| Корни курсов | `src/data/courses.ts`, публичные ссылки Диска | Менять конфигурацию и проверять корневые и вложенные пути; доступность зависит от публичной ссылки. |
| Метаданные поиска | `data/search/*.csv`, снимок каталога | При необходимости `search:sync`, затем разметка, `search:validate`, `search:build` и проверка coverage. Workbook — рабочая форма, а не источник истины. |
| Расписание | Публичные данные LKS и проверенные JSON в `public/data/schedule/` | Pipeline `schedule:sync` собирает и проверяет набор до замены; `schedule:validate` проверяет локальный результат. Обновление семестра требует проверки `weekOneStart`. |
| Личные данные и аналитика | D1 соответствующего окружения | Изменения схемы только через миграции; beta и production изолированы. |

Полные команды и ограничения приведены в [search.md](search.md), [schedule.md](schedule.md), [data-model.md](data-model.md). Сетевые sync-команды обращаются к внешнему источнику и отличаются от локальных проверок в CI.

## Разработка и проверка

Нужны Node.js 22 и npm. После `npm ci` команда `npm run dev` запускает Vite; `npm run dev:telegram` дополнительно создаёт временный Quick Tunnel для ручной проверки через Telegram. Публичный адрес Worker при необходимости задаётся `VITE_ANALYTICS_API_BASE`; образец — `.env.example`. Сам по себе туннель не подтверждает корректность настройки бота или реального WebView.

`npm run qa` последовательно выполняет lint, проверку типов, Vitest и Node/Worker тесты, проверки подготовленных данных поиска и расписания, production-сборку и Playwright. Отдельно доступны `npm test`, `npm run test:ui`, `npm run build`; UI-тесты используют управляемые фикстуры Telegram и Диска. Они не доказывают работу физического устройства, реального webhook или внешнего источника. Состав и известные ограничения проверок — [testing.md](testing.md), [known-issues.md](known-issues.md).

## Окружения и выпуск

`beta` — обычная ветка разработки и предпросмотра; `main` — production. Для каждой среды предусмотрены отдельные Worker, D1, origin и секреты; публичные файлы расписания могут быть одинаковыми, приватные данные между средами не копируются. `wrangler.toml` описывает binding и несекретные настройки, а секреты задаются средствами Cloudflare. Pages публикует статический frontend, Worker разворачивается отдельно; изменение одного компонента не означает автоматического обновления другого.

Обычный путь: синхронизировать `beta`, внести изменение, выполнить подходящие проверки и проверить Beta Mini App. Production release требует явного запроса пользователя и отдельного полного процесса, включая синхронизацию веток, миграции при необходимости, развертывание и smoke. Актуальная процедура и условия — [development-workflow.md](development-workflow.md) и [deployment.md](deployment.md); не используйте исторические записи о версиях развертывания как доказательство текущего состояния.
